二、MapReduce

主要流程：

  • Master：分配任务
  • Worker：干活的（Map / Reduce）

细节：

1、如何分配工作

  • MapReduce 会先把输入数据切成很多 input splits任务，通常每个 split 对应一个 map task

  • Master 维护所有 map/reduce task 的状态，哪个 worker 空闲了，就给它分配一个还没做的 task

  • Master 优先把 task 分给“数据本地”的 worker，或者同机架上的 worker

  • Worker 动态领取任务（空闲时领取）

  • 整个过程为：调度式分配

2、如何将MapReduce代码发给各个服务器
  • 代码提前部署在所有机器上
  • 把需要的文件代码先传到共享存储上，再由worker动态加载
3、如何跟踪进度
  • Master 会记录每个 task 的状态（三个状态）：
    • idle
    • in-progress
    • completed
  • Worker 在执行中会：
    • 接受任务
    • 定期汇报状态
    • 完成自己的任务后汇报结果位置
  • 一个 mapreduce 任务什么时候算完成
    • 所有 map 任务完成 + 所有 reduce 任务完成
4、如何移动数据从 map 到 reduce（shuffle）

  • Map worker 执行完 map 任务时，生成（key , value）对

  • 按分区函数（Partition）把中间结果切成 R 份（R 是 reduce task 数量）

    这些中间结果先写到 Worker 自己的本地磁盘

    • 通俗：一个快递分拣员（Map）根据目的地（key 的 hash）把包裹分成 3 堆：一堆寄北京，一堆寄上海，一堆寄广州
    • 每个Map Worker会生成R个文件

  • Reduce worker 通过网络去各个 map worker 拉取属于自己分区的数据

    • 通俗：北京站的收货员（Reduce 0）自己开着货车，跑到每个分拣员（Map Worker）的摊位，把写着“北京”的筐搬上车，拉回自己的仓库

  • Reduce worker在拉完自己对应的数据后对数据进行排序（归并排序 - 按key排序）、归并，再执行其自身的 reduce 函数（如求和/求平均值）

5、负载均衡，如何用尽所有服务器
  • 把总任务拆成大量小任务
  • 动态调度：快的机器多做，慢的机器少做
  • 数据本地性优先：减少网络传输，加速
  • 推测执行：对于特别慢的“拖后腿任务”，Master 可以在另一台机器上再启动一个副本，谁先做完用谁
6、错误恢复（三种情况）

  • Map Worker 挂了

    • 它已经完成的 map task 通常也要重做

      因为 map 中间结果存在这个 worker 的本地磁盘上，机器挂了数据就没了

  • Reduce Worker 挂了

    • 它已完成的 reduce task 一般不用重做

      因为 reduce 输出通常已经写到分布式文件系统里了

  • Master 挂了：主控容错机制

  • Master发现Worker出错的过程：

    • Master 通过超时、心跳等方式发现 worker 失联
    • 把未完成任务重新标为 idle
    • 分配给其他 worker
7、处理文件分布
  • MapReduce 通常运行在像 GFS 这样的分布式文件系统之上
  • GFS 的特点：
    • 文件被切成多个 chunk
    • 每个chunk会复制到多台机器上
  • 在 Google 的 MapReduce 架构里，所有 worker 所在机器都能访问 GFS（否则它们没法读输入，也没法把最终结果写回去）

三、Go并发

1、相关概念
  • 程序：静态代码
  • 进程：程序运行起来之后成为进程
  • 线程：进程内的执行流，负责实际执行代码
  • CPU：执行线程指令的硬件单元
  • 总结：进程是资源容器，线程是执行单位，CPU 是执行硬件
2、线程（Thread）
  • 线程是程序内部一条持续向前执行的独立控制流
  • 同一进程中可以存在多个线程
  • 同一进程的线程共享同一地址空间，通信开销低；但正因为共享资源，也存在相互干扰的风险
3、线程 和 进程 的关系

  • 定义：进程是运行中的程序实例，线程是进程内部具体执行任务的单元

    进程 > 线程

  • 同一进程的线程共享大量资源，但每个线程拥有独立的执行状态

4、线程的作用
  • 提升响应性：当某线程等待磁盘或网络 I/O 时，其他线程可继续执行
  • 逻辑结构清晰：将不同职责分配给不同线程，程序组织更为清晰
  • 多核利用：多线程可调度到多个 CPU 核心上，实现真正的并行执行
5、并发 vs 并行（重要）

  • 定义：

    • 并发（Concurrency）：多个任务在同一时间段内均有所推进
    • 并行（Parallelism）：多个任务在同一时刻真正同时执行

  • 关系：并行 ⊂ 并发

    并行是并发的一种特殊情形，并发不一定并行

  • 主要区别（*）

    • 并发：交替推进
    • 并行：同时推进
6、Go中的并发：goroutine
  • goroutine 是 Go 运行时管理的轻量级执行流，不是操作系统线程
  • 启动一个新的goroutine：go doWork()
7、goroutine和操作系统线程（OS）之间的关系
  • Go 运行时将大量 goroutine多路复用到少量操作系统线程上运行
8、共享内存（Shared Memory）
  • 同一进程的多个线程通常共享以下信息：
    • 全局变量
    • 堆内存
    • 已打开的文件
    • 进程地址空间
  • 好处：线程间通信简便，数据共享效率高
  • 风险：多个线程的操作可能相互干扰，导致数据不一致
  • 多线程的执行顺序是交错的会引发问题
9、竞争条件（race condition）

  • 定义：程序的执行结果依赖于线程调度的相对时序，而某些时序会导致错误的结果

  • 特征：

    • 偶发性错误，很难复现
    • 代码看起来正确
    • 高并发或特定负载下才暴露

  • 例：n = n + 1 问题

    造成问题：lost update（丢失更新）

    误解：”只有一行代码，就不会有并发问题”

    n = n + 1为三步：内存读n的当前值+执行加法运算+结果写回内存

10、原子性（atomicity）
  • 定义：一个操作要么完整执行，要么完全不执行，执行过程不可被中断或观察到中间状态
  • 若某操作不具备原子性，其他线程便可能在其执行中途介入，引发数据不一致
11、临界区（critical section）

  • 定义：不能被多个线程同时执行的一段代码

  • 判断是否为临界区：

    • 是否访问了共享数据？
    • 多个线程同时执行是否会导致数据不一致？

    两个都是”是” → 这就是临界区

    临界区是需要受到保护的关键代码段

    竞态条件经常发生在临界区没有被正确保护的时候

12、互斥（mutual exclusion）
  • 定义：同一时刻最多允许一个线程进入临界区执行
  • 作用：防止多个线程同时修改同一份共享状态，从而保证数据的一致性
13、锁（lock）
  • 锁是实现互斥最常见的机制
  • 作用：确保共享状态不被同时破坏
  • 锁的使用：
    • 进入临界区之前加锁
    • 离开临界区之后解锁
  • 锁的效果：
    • 持有锁的线程可进入受保护代码段
    • 其他线程在获得锁之前须阻塞等待
14、Go中的互斥锁（sync.Mutex）

  • var mu sync.Mutex

  • mu.Lock() 加锁

  • mu.Unlock() 解锁

  • 或者直接在加锁后用defer mu.Unlock()

  • 锁解决的核心问题：共享状态被并发访问时的正确性保障

  • 锁的使用原则：

    • 只在确实需要保护的临界区加锁，而非在所有地方加锁

  • 引入锁的代价：

    • 线程等待与阻塞
    • 并发度降低，吞吐量下降
    • 锁使用不当可能引发死锁（deadlock）
15、并发的目标
  • 可并发的部分尽量并发，需要保护的部分必须互斥
16、总结

  • 线程 → 操作系统调度的最小执行单位

  • 进程 → 资源分配的基本单位

  • 并发 → 多线程在同一时间段内交替推进

  • 共享内存 → 线程间协作方便，但存在相互干扰的风险

  • race condition → 执行顺序的差异导致结果不一致（问题）

  • critical section → 需要保护的关键代码段（地方）

  • atomicity → 操作若不可分割，则不会出现中间状态被观察的问题

  • mutual exclusion → 同一时刻仅允许一个线程执行临界区

  • lock → 实现互斥最常见的机制

  • 并发不等于并行：并行 ⊂ 并发

  • 共享内存在提供通信便利的同时，也引入了竞争风险

  • 锁的目的不是提升性能，而是首先保证正确性

  • 并发强调“多个任务均在推进”，并不要求每一时刻都真正同时执行

    判断：并发就是多个线程同时执行（错）

  • 判断：只有一行代码，就不会有并发问题（错）

    单行高级语言代码在底层通常对应多个机器指令

  • 判断：使用更多线程，程序一定更快（错）

    多线程频繁竞争同一把锁时，等待开销可能使程序比单线程还慢

  • 判断：使用 Go 或 goroutine，共享数据自动是安全的（错）

    只要多个 goroutine 访问共享数据，且没有适当的同步机制，race condition 依然存在

  • 并发程序的核心矛盾是：

    多条执行流需要同时推进，但它们可能访问同一份共享状态

  • 并发使多个任务得以同时推进；共享内存使它们容易相互干扰；锁通过互斥机制保护临界区，确保共享状态的一致性

三、并发协作

1、回顾

  • Race Condition

    • n++案例，两个 goroutine 同时读写同一变量，结果取决于调度顺序，不可预测，导致 Lost update

  • Critical Section

    • 需要保证同一时刻只有一个执行流进入，进入前加锁，退出后解锁

  • Mutex

    • Lock() 拿不到时，当前 goroutine 阻塞
    • 同一时刻只有一个 goroutine 持有锁
    • Unlock() 之后，等待中的 goroutine 才能继续
    • 注：只有互斥，还没有协作
2、互斥 vs 同步
  • 互斥：防止多个执行流同时进入临界区
  • 同步：控制执行顺序，让某些步骤必须「先发生」
  • 总结：互斥解决「不能一起做」，同步解决「必须按条件做」
3、忙等（busy waiting）
  • 定义：一个线程（或 goroutine）在等待某个条件满足时，不释放 CPU，而是一直在那里反复检查条件，做“无用功”
  • 造成的问题：
    • CPU空转，浪费CPU
    • 并发多时，大量忙等会让 CPU 100%，其他任务无法执行，造成系统崩溃风险
4、条件同步（condition synchronization）

  • 为实现：

    • 条件不满足：休眠
    • 条件满足：被唤醒
    • 被唤醒后：继续执行

  • 避免忙等这个问题

  • 定义：

    • 一个执行流等待某个条件成立
    • 另一个执行流在条件成立后通知它继续

  • 条件同步在等：状态变化，如：

    • 缓冲区非空
    • 缓冲区非满
    • 某任务完成
    • 某阶段全部结束
    • 某结果已经算出来
5、条件同步经典模型：producer - consumer

  • Producer：

    • 生成 item

    • 放进缓冲区

  • Consumer：

    • 从缓冲区取 item
    • 处理 item

  • 关键条件：

    • 缓冲区空：消费者要等
    • 缓冲区满：生产者要等
6、Python的GIL

  • Global Interpreter Lock，GIL

    同一时刻只允许一个线程执行 Python 字节码

  • GIL解决了：

    • Python内部用引用计数管理内存，而引用计数的修改不是原子操作，因此GIL保证了运行时内部的安全

  • GIL的代价：

    • CPU 密集型任务无法利用多核（因为GIL只允许同一时间只有一个线程在运行，而多核CPU按理说是可以多个线程同时执行任务的）

  • GIL和Go的区别：

    • GIL：运行时自动帮你加锁；简化了内存管理；但限制了并行
    • Go：
      • 没有 GIL
      • goroutine 真正在多核上并行
      • 需要用 mutex / channel 显式管理共享状态
7、Channel
  • 定义：一根带类型的通信管道，可以发送数据、接收数据，顺便完成同步
  • channel的创建，发送，接受
  • make函数（专门用作创建三种类型）
    • s := make([]int, 3) // slice
    • m := make(map[string]int) // map
    • ch := make(chan int) // channel
8、无缓冲 Channel & 有缓冲 Channel

  • 无缓冲 Channel：

    • 发送和接受必须同时准备好，否则阻塞

      啥意思？

      • 发送和接受需要放在两个不同的goroutine里面

        一个负责发；一个负责接受（两个goroutine）

      • 典型错误

        这里阻塞的原因：没有接收者

  • 有缓冲 Channel：

    • 第二个参数为缓冲区大小

    • 核心规则：缓冲没满就能发，缓冲没空就能收

9、producer-consumer的带channel的Go语言版本
  • producer部分：
    • 如果不关闭close(ch)，则会：
      • consumer部分的range ch会一直等着接受，导致死锁
      • close(ch)意思：告诉consumer不会再发送新的值了
  • consumer部分：
    • for x := range ch的含义：
      • 不断从 ch 中接收值，每次取一个赋给 x
      • 循环会一直执行，直到 ch 被关闭
10、接收的两值形式
  • x,ok := <- ch
    • ok = true：成功收到值
    • ok = false：channel已关闭且没有剩余值

    • 收发消息，顺便同步
